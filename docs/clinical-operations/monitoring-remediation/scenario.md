# 场景规约：培训记录缺失／版本不匹配

版本：0.1 设计切片。日期：2026-10-26。
状态：供评审；不是临床系统、法规合规认证或医疗建议。

## 1. 已确认范围

首个业务场景是临床试验监查发现与整改。具体发现是指定中心人员的培训记录缺失，或记录对应的方案版本与适用要求不匹配。

用户确认的角色规则：
- 中心协调员提交整改材料。
- CRA 复核材料。
- CTM 审批关闭发现。
- Agent 只能检查、建议和受限分派；不能批准整改计划、替代 CRA 复核或关闭发现。

本轮只交付场景规约与验收案例。不实现解析器、运行时或管理界面。

## 2. 合成案例与非目标

合成研究 `STUDY-DEMO`，中心 `SITE-DEMO`，人员 `STAFF-DEMO`。监查发现 `FINDING-DEMO` 的适用要求快照 `REQ-H1` 指定方案 `PROTOCOL-V3` 的培训记录。

初始状态：旧记录明确对应 `PROTOCOL-V2`。这是“已确认版本不匹配”，不是 Unknown。另一个测试变体是经完整清单核对后确认没有记录。只有检索不完整、材料不可读或适用版本不能确定时，才表示信息不足或未决。

这些 ID 与哈希都是可读的合成标签，不是实际内容摘要。实际实现必须使用规范化内容计算哈希，不得把标签当作安全凭证。

不包含：
- 受试者身份、源病历、临床数据修改、诊断或治疗判断。
- 自动判定培训已实际发生，或仅凭上传文件判定其真实性。
- 把所有整改自动归为正式 CAPA。是否需要 CAPA 由显式策略和有权限的人决定。
- 自动宣布中心可以开展研究、决定人员可以执行研究活动。
- 真实系统写入、邮件发送或监管提交。

首版使用合成材料和模拟执行。这是本设计的安全边界，不是已验证的真实组织 SOP。

## 3. 成功与安全条件

成功：指定发现被 CTM 在有效权限内关闭；关闭指向 CRA 已通过复核的同一证据包和同一适用要求快照，且该动作具有完整审计引用。

硬边界：
1. 上传成功不等于证据合格。
2. 补齐任务完成不等于发现关闭。
3. CRA 通过不等于 CTM 已批准关闭。
4. 证据、要求、复核范围或审批对象发生实质变化后，旧结论不得自动继承。
5. 关键条件 Unknown 或未决时，不得关闭。
6. 关闭不删除原始发现，也不抹去迟延、历史版本不匹配或其他偏差。
7. 未授权动作不能改变状态，不能扣除任务预算，也不能产生虚假的成功事件。

目标是最终合法关闭；目标未达到不等于每个中间状态违规。暂停、退回和升级可构成安全的部分执行。Core 的 `eventually` 目标需要完整轨迹才能判断，首版不承诺自动决定无限轨迹的终止性。

## 4. 角色与权限

以下是本切片的业务政策，不宣称为通用法规要求。

| 角色 | 允许 | 禁止 |
|---|---|---|
| 中心协调员 | 在有效 Grant 内提交该中心该发现的材料 | CRA 复核通过、CTM 关闭、改写旧证据 |
| CRA | 记录独立复核、提出退回、请求升级 | 直接关闭；代替中心提交后自审同一证据 |
| CTM | 对精确证据与要求版本执行关闭；授权范围内重开或更新要求 | 使用失效复核关闭、越研究或中心范围执行 |
| Agent | 只读检查、生成候选解释和整改计划；有效 Grant 内创建或分派模拟任务 | 代答用户、批准计划、记为 CRA 复核者、关闭发现 |

身份必须由可信认证上下文绑定。动作名称、参数里的角色字符串、签名或模型自报身份都不能授予权限。

采用业务角色和主体身份双重隔离：本切片的协调员、CRA、CTM 由不同主体担任；CRA 不得是该次材料提交者。CTM 与 CRA 也不同。组织若要变更这一策略，必须形成显式政策修订，不静默放宽。

Delegation 默认拒绝；显式 deny 优先。每次执行都检查 Grant 的研究、中心、发现、动作、期限及资源范围。Core 前置条件成立不代表有权执行。

## 5. 状态机

| 状态 | 含义 |
|---|---|
| OPEN | 发现已登记；可以澄清和提出整改计划 |
| IN_REMEDIATION | 精确整改计划已被有权人员接受；补齐任务进行中 |
| SUBMITTED | 证据包已提交；尚未得到有效 CRA 通过结论 |
| CHANGES_REQUIRED | CRA 退回；需修正或补充 |
| REVIEWED | CRA 已通过，且复核仍绑定当前证据和要求 |
| CLOSED | CTM 已按当前有效范围批准关闭 |

Escalation 是独立的阻断记录，不是用一个状态替代上述业务生命周期。阻断可以只影响关闭，也可以影响具体任务，须记录影响范围和解除权限。

| 转移 | 触发与执行者 | 必要条件 |
|---|---|---|
| OPEN → IN_REMEDIATION | 记录计划接受；受授权记录服务 | 有权人员在 Exchange 接受确切计划哈希；系统不冒充其接受 |
| IN_REMEDIATION / CHANGES_REQUIRED / SUBMITTED / REVIEWED → SUBMITTED | 协调员提交或替换证据 | 作用域正确；证据快照可访问且内容摘要已核对；清空旧有效复核绑定 |
| SUBMITTED → REVIEWED | CRA 通过复核 | 要求、证据同版本；满足第 6 节；有有效 HumanReview 凭证 |
| SUBMITTED / REVIEWED → CHANGES_REQUIRED | CRA 退回 | 理由与目标版本明确；使旧通过结论不再用于关闭 |
| REVIEWED → CLOSED | CTM 关闭 | 第 7 节全部满足；有效授权和精确行动批准 |
| REVIEWED → SUBMITTED | 有受限 Grant 的复核失效记录服务 | 已确认当前复核过期、撤销或依赖失效；清空有效复核绑定，保留历史 |
| 任意状态 → OPEN | CTM 更新适用要求 | 新要求已获有权人员接受；旧复核、计划和关闭投影失效；保留历史 |
| CLOSED → OPEN | CTM 重开 | 挑战或证据失效依据明确；不覆写旧关闭事件 |

计划形成属于 Exchange；权限属于 Delegation；复核凭证属于 Assurance。Core 示例只接收它们经过边界检查后投影的事实。不能让 Core 因某个角色或接受事件而改变逻辑真值。

## 6. 证据与复核门槛

证据包必须绑定：研究、中心、发现、人员、方案版本、适用要求哈希，以及不可变材料清单。原始上传中的字段只是断言，不能直接升级为已建立事实。

复核至少检查：
- 人员、研究、中心及发现匹配。
- 方案版本与已确认适用要求一致；不是机械使用“最新版本”。
- 要求中的材料清单齐全且可读。
- 日期、签署或确认要求按显式领域政策检查；本切片不编造统一签署规定。
- 来源、真实性检查结果及其覆盖范围被记录。
- 迟延或此前未满足要求是否需要关联处置；不能通过补交材料抹去历史问题。
- 所有阻断项已解除，或存在明确政策允许且有权人员接受的处置；不得由 Agent 自选忽略。

`HumanReview Pass` 表示指定范围内的审核结论，不表示培训真实性的普遍证明或全面法规合规。字段 `complete`、`readable`、`authenticityEstablished`、`policyChecksPass` 是受信复核流程的投影，不能仅复制上传者勾选框。

Assurance 凭证必须绑定规约、目标证据、要求上下文、审核者及方法版本、覆盖范围、假设和有效期。复核输入变化后，凭证失效或进入待重估状态。状态缓存保存精确 `activeReviewHash`；有效性判定必须针对该凭证，不能用同一材料的任意新旧 Pass 替换。已确认失效时，由受限记录服务将 REVIEWED 降为 SUBMITTED 并清空绑定，再由 CRA 重新复核。有效性 Unknown 时先阻断关闭，不冒充已确认失效。CLOSED 后的失效触发挑战及升级，由 CTM 重开；历史关闭事实仍保留，不代表当前认可其继续有效。

## 7. 关闭判定

只有以下各项均成立才允许关闭：
1. 状态为 REVIEWED。
2. 当前证据包与 CRA 通过结论的证据哈希一致。
3. 当前要求与 CRA 通过结论的要求哈希一致。
4. 证据内容、作用域与政策检查均已建立；未知不算通过。
5. CRA 复核凭证仍有效，覆盖当前材料及要求。
6. 无阻断性歧义、争议或升级项。
7. CTM 身份、角色、Grant 有效且符合人员隔离。
8. CTM 批准精确关闭计划哈希；批准绑定发现、证据、要求和复核凭证。
9. 执行前再次核对版本；检查与写入之间发生变化则拒绝并重新评估。

关闭事件必须引用原始发现、接受的计划、当前证据、要求、CRA 凭证、CTM 批准和执行 Grant。不能只存 `closed=true`。

## 8. 澄清、期限和升级

典型意图：“把培训记录的问题处理掉。”系统必须澄清：哪个发现、人员、适用方案，以及“处理”是准备材料、提交复核还是申请关闭。

AI 可以提出候选解释；只有有权回答者的真实回答和精确接受才能消除相应未决项。所有非阻断工作可以继续；阻断范围必须明确。

整改期限来自显式计划或政策，不在本切片虚构固定天数。时间未知时标记 `open`，不生成虚假逾期结论。逾期触发任务升级，不自动等同于证据无效或禁止今后关闭；是否阻断关闭取决于显式迟延处置政策。

## 9. 文件及实现边界

- `ontology.gil`：最小领域类型和纯关系。
- `workflow.gil`：Core 的状态与动作契约示意。
- `acceptance.md`：合成夹具与分层验收案例。

每个 `.gil` 文件只有一个顶层定义，避免现有 EBNF 的 `document` 仅接受一个定义的问题。示例不加入无正式 EBNF 的 Grant、Accept 或 Attestation 语法。

当前没有解析器或测试运行器。示例经过规范人工审查，不声称已通过机器解析或形式证明。外部动作适配器、时间模型、内容摘要算法、标准库及外层序列化仍需实现时定义。
